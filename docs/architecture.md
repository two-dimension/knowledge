# 砚知系统架构方案

## 一、设计原则

1. **原始材料与研究判断分层。** 原话、转写、AI 摘要、研究员判断是四种不同对象，不能互相覆盖。
2. **以观点为知识单元。** “某份纪要”只是容器；真正可复用的是带时间窗、标的、证据、反证条件和版本的观点。
3. **检索必须可回溯。** 每个回答都要能定位到谈话、说话人、原始片段和当时上下文。
4. **先治理、后智能。** 没有授权、敏感等级和知悉范围的数据，不进入模型检索范围；访问与操作审计由公司内部平台统一承接。
5. **允许分歧长期存在。** 系统同时存储支持证据、反对证据与未决问题，不自动把多数口径当作事实。

## 一点五、开源项目借鉴边界

- **AnythingLLM / Open WebUI：** 借鉴“工作区 + 对话 + 来源”的产品结构，在砚知中落为研究问答与逐条引用，不移植其完整运行时。
- **Haystack：** 借鉴显式、可观察的处理流水线，让采集、结构化、检索、重排、引用和人工确认可以分别检查与替换。
- **LlamaIndex：** 借鉴按语义切片、携带元数据并返回引用的检索契约；当前用 D1 实现，将来可替换托管向量召回。
- **LightRAG：** 仅预留实体与关系扩展方向，数据规模和查询复杂度达到阈值前不引入图数据库或本地模型。

## 二、业务闭环

```text
采集 Capture
  └─ 录音 / 速记 / 参与者 / 场景 / 授权 / 敏感等级
        ↓
处理 Process
  └─ 转写 → 说话人分离 → 主题分段 → 实体识别 → 去重
        ↓
结构化 Structure
  └─ 事实 / 观点 / 预测 / 传闻 → 行业 / 公司 / 人物 / 时间窗
        ↓
验证 Verify
  └─ 可证伪假设 → 指标 / 阈值 / 负责人 / 截止时间 / 结果
        ↓
复用 Retrieve
  └─ 字段加权 + 词项切片 + 时间/置信度重排 → 原文级引用
        ↓
记忆 Memory
  └─ 新证据触发更新 → 保留旧版本 → 记录命中率和漂移
        ↓
编译 Compile
  └─ 原始谈话 → 行业页 / 公司页 / 研究笔记 → 双向链接 → Markdown 导出
```

## 二点五、LLM 原生 Wiki 层

参考“raw 数据由 LLM 增量编译为 Markdown Wiki”的工作方式，砚知新增独立的编译层：

- 原始谈话、音频和逐字稿继续作为不可覆盖的 raw 层。
- 编译器按行业、公司和投资命题生成 Markdown 页面，并使用 `[[双向链接]]` 连接相关页面。
- 研究问答结果可以一键归档为研究笔记，作为下一轮检索与编译的知识增量。
- 健康检查持续发现缺证据、低置信度、未绑定实体和验证逾期问题。
- 页面可直接导出 `.md`，兼容 Obsidian；当前不要求安装 Obsidian 客户端。

## 三、无 Docker 的轻量检索实现

当前版本不部署 RAGFlow、Elasticsearch、Milvus 或本地推理模型。系统将原始录音保存在 R2，将谈话、任务、审计和检索切片保存在 D1：

| 层级 | 当前实现 | 后续可替换项 |
| --- | --- | --- |
| 原始材料 | R2 音频对象 | 企业对象存储 / 私有云 S3 |
| 业务数据 | D1 结构化记录 | PostgreSQL |
| 可检索切片 | `search_chunks`，按标题、摘要、观点、逐字稿分层 | Cloudflare AI Search / OpenSearch |
| 召回与排序 | 中文词项和二元组、字段权重、精确短语、时效性、置信度 | hybrid embedding + reranker |
| 引用 | 返回 chunk id、类型、摘要和匹配分数 | 说话人 + 时间码定位 |

这一路径的核心目标是先把“可搜索、可引用、可审计”跑通，而不是在小样本阶段维护完整 RAG 平台。搜索接口与界面使用稳定的命中结果结构，后续切换 Cloudflare AI Search 时不需要重写前端。

### 推荐切片策略

- 一级：一场谈话（conversation）
- 二级：连续话题段（topic segment，约 2–8 分钟）
- 三级：可独立引用的说话轮次（utterance chunk）
- 每个片段同时保存前后窗口、说话人、时间码、公司/行业/指标实体、敏感标签
- 观点抽取后不直接覆盖片段，而是创建 `thesis ↔ evidence_chunk` 关联

### 推荐检索流程

1. 将问题解析为公司、行业、时间、人物、指标、观点状态和知悉范围。
2. 先做权限过滤和证券主数据规范化。
3. 当前执行 D1 词项召回；数据量扩大后增加托管向量召回。
4. 按字段、短语命中、时效性和置信度进行融合排序。
5. 生成回答前检查证据覆盖度；证据不足时明确返回“尚无足够材料”。
6. 输出逐条引用、原文定位、置信度来源和相反证据。

### 研究问答的当前降级策略

研究问答先调用 D1 轻量混合召回，将命中的观点、摘要和原话切片按相关度拼成“证据摘要”，同时返回覆盖度、置信度和原文入口。该模式不依赖大语言模型，也不会在证据不足时补写常识。未来接入合规批准的模型后，只替换检索后的总结器，权限过滤、召回、引用和审计流程保持不变。

## 四、生产架构

```text
Web / Mobile Web
  ↓ SSO + RBAC/ABAC
Application API
  ├─ Conversation Service
  ├─ Thesis & Verification Service
  ├─ Entity / Security Master Service
  └─ Audit & Compliance Service
        ↓
Lightweight Ingestion
  ├─ 托管 ASR + speaker diarization
  ├─ 观点 / 摘要 / 原话分层切片
  ├─ 规则结构化 + human review
  └─ D1 检索索引更新
        ↓
Storage Layer
  ├─ D1：业务实体、检索切片、转写任务、审计
  ├─ R2：录音和原始文件
  ├─ Cloudflare AI Search（可选）：托管混合检索
  └─ 企业数据仓库（生产阶段）：主数据、持仓与行情
```

当前 MVP 使用 D1 + R2 保持轻量，不需要 Docker；检索在没有外部模型和密钥时仍可工作。

## 五、安全与合规

- 部署：优先公司内网或私有云，不把原始录音暴露在公共互联网。
- 身份：SSO + MFA；按部门、行业组、项目组、敏感等级组合授权。
- 数据：传输和静态加密；对象存储使用短时签名 URL；关键字段可单独加密。
- 平台集成：查看、搜索、导出、下载原文和权限变更等审计能力由公司内部平台统一提供，知识库前端不单独展示审计模块。
- 合规：录音授权确认、疑似内幕信息拦截、个人敏感信息脱敏、保留期和删除审批。
- 模型：默认不允许供应商留存或训练；生产环境应支持本地模型或零留存合同。

## 六、从 MVP 到生产的三阶段

### 阶段 1：方法验证（2–4 周）

- 选一个行业组、100–300 条历史谈话。
- 确认数据字典、结构化模版、证据等级和验证闭环。
- 目标：结构化确认平均小于 8 分钟，搜索 Top-5 有效命中率大于 80%。

### 阶段 2：检索与集成（4–8 周）

- 配置合规批准的托管 ASR、证券主数据和持仓快照。
- 数据量和检索评测达到阈值后启用 Cloudflare AI Search 托管混合检索。
- 上线带引用的研究问答、观点对比和组合关联提醒。
- 目标：引用覆盖率 100%，错误权限召回为 0，研究员周活大于 70%。

### 阶段 3：机构记忆（持续）

- 上线观点版本、自动到期、历史命中率、信息源校准和研究复盘。
- 逐步加入公告/财报/卖方研报等外部证据，但与内部口径明确分层。

## 七、关键指标

- 入库完整率：具备场景、人物、授权、行业、敏感等级的谈话占比
- 结构化确认时长：从上传到研究员确认的 P50 / P90
- 检索 Precision@5、无结果正确率、引用可定位率
- 观点可证伪率、按期验证率、命中率、观点半衰期
- 权限误召回数、敏感内容导出次数、审计缺失数
- 复用率：被搜索、引用、加入验证或关联组合的知识条目占比

## 八、大语言模型的角色

大语言模型不是底层存储、权限控制、全文检索和审计的必需组件。当前版本使用规则引擎即可完成演示级字段回填。生产环境建议在三个位置接入模型：

1. 入库时：区分事实、观察、观点、预测和传闻，抽取实体、时间窗与候选假设。
2. 检索后：基于经过权限过滤和重排的证据生成带引用回答。
3. 验证时：将模糊判断改写为指标、阈值和反证条件，但由研究员最终确认。

模型不应负责权限决策，也不应直接改写原始逐字稿。所有模型输出均保存模型版本、提示词版本、输入证据和人工修改痕迹。
